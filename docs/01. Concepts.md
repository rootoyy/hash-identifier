# Introduction

A hash function acts like a digital one-way machine. It takes any piece of data — a single word, a document, or an entire video —and transforms it into a unique, fixed-length string of characters (such as `a3f9b2`). This output is known as a **hash value**, **digest**, or **checksum**.

# Key Properties of Cryptographic Hashes

- **Deterministic ($h(m_1) = h(m_2) \iff m_1 = m_2$):** The exact same input will always produce the exact same hash output. This allows systems to safely store and verify passwords by re-hashing user input at login.
    
- **Fixed-Length Output:** Regardless of the input size, the output length is constant and depends entirely on the algorithm used (e.g., MD5 yields 32 hex characters, while SHA-256 yields 64). This fixed length is the primary indicator used to identify unknown hash types.
    
- **Pre-image Resistance (One-Way):** Computing the hash from an input is computationally easy, but reversing the process ($h^{-1}(y)$) is practically impossible. Identifying an unknown input requires brute-force guessing or dictionary attacks using tools like Hashcat.
    
- **Avalanche Effect:** A minimal change in the input (even a single bit) produces a drastically different and uncorrelated hash output.
    

# Mathematical Definition 

A hash function $h$ is a deterministic algorithm defined as a mapping from an arbitrary-length binary string to a fixed-length binary string of $k$ bits:

$$h: \{0, 1\}^* \to \{0, 1\}^k$$

Where:

- $\{0, 1\}^*$ represents the set of all binary strings of any arbitrary length.
    
- $\{0, 1\}^k$ represents the set of all binary strings of fixed length $k$.

# Why do we hash passwords

Storing plaintext passwords in a database poses a severe security risk

| **username** | **password** |
| ------------ | ------------ |
| **alice**    | hunter2      |
| **bob**      | letmein      |
A single database breach compromise all user credentials directly. Because users frequently reuse passwords across multiple services, an attacker instantly gains unauthorized access to external accounts (email, backing, etc).

To mitigate credential leaks, applications store cryptographic hash outputs instead of raw inputs: 

|**username**|**password_hash**|
|---|---|
|**alice**|`f52fbd32b2b3b86ff88ef61f3d728045`|
|**bob**|`0d107d09f5bbe40cade3de5c71e9e9b7`|

# Fast vs Slow hashes

An attacker with access to a leaked database of hashes cannot reverse them directly, forcing them to run dictionary or brute-force attacks by hashing candidate passwords until a match is found
- Fast Hashes (MD5, SHA-1, SHA-256): Optimized for high-throughput data integrity checks. A modern GPU can compute billions of guesses per second, making fast hashes vulnerable to offline brute-force cracking 
- Slow / Work-Factor Hashes(Bcrypt, Argon2, PBKDF2): Designed with configurable computational cost (work factors) and memory requirements. By reducing cracking speed to thousands of guesses per second, they make large-scale offline attacks computationally expensive and impractical.

# Identification signals in hash analysis 

A hash string exposes up to three structural clues: Prefix, Length, and Character Set (Charset). 
A detection engine evaluates these signals in order of specificity, moving from strongest to weakest.
## Signal 1: Prefix (High Confidence)

Modern password hashing algorithms utilized the standardized PHC (Password Hashing Competition) string format. These self-describing strings explicitly state the underlying algorithm and configuration parameters: 
- Argon2id: `$argon2id$v=19$m=65536,t=3,p=4$...` (Specifies algorithm, version, and cost factors)
- Bcrypt: `$2b$12$...` (Specifies variant `2b` and cost factor `12`).
Matching an explicit prefix yields a High Confidence classification. Legacy hash functions (such a standalone MD% or SHA-1) lack prefixes, outputting raw digests only

| **Prefix**       | **Algorithm**     | **Common Context**                             |
| ---------------- | ----------------- | ---------------------------------------------- |
| `$argon2id$`     | **Argon2id**      | Modern web applications (Current standard)     |
| `$2b$`           | **Bcrypt**        | Enterprise web applications                    |
| `$6$`            | **SHA-512 Crypt** | `/etc/shadow` file on Linux distributions      |
| `$apr1$`         | **Apache MD5**    | Apache HTTP basic authentication (`.htpasswd`) |
| `$P$`            | **phpass**        | WordPress and PHP platforms                    |
| `pbkdf2_sha256$` | **Django PBKDF2** | Django framework defaults                      |
| `{SSHA}`         | **Salted SHA-1**  | LDAP directory services                        |
## Signal 2: Length (Medium / Low Confidence)

Hash functions emit fixed-length output, if ii does not have prefix and have 64 hex characters, is came from the 256-bit hash family (SHA-256, SHA3-256, BLAKE2s-256, RIPEMD-256). Each algorithm always emits the same number of bytes:

|**Algorithm**|**Output (Bytes)**|**Length (Hex Chars)**|
|---|---|---|
|**MD5**|16|32|
|**SHA-1**|20|40|
|**SHA-224**|28|56|
|**SHA-256**|32|64|
|**SHA-384**|48|96|
|**SHA-512**|64|128|
Length narrows the field but rarely picks a unique winner. 32 hex characters could be MD5, NTLM, MD4 or RIPEMD-128, they all produce 128 bits of output. So when the tool matches on length, it reports MEDIUM confidence for the most likely algorithm at that length and LOW for the rest. 

## Signal 3: Charset 

The character set of the hash narrows thing further. Three common alphabets show up: 
- **Hex:** only `0-9a-f` (or `0-9A-F` if uppercase). Used by raw MD5, SHA-family, NTLM, etc.
- **Base64-ish:** `0-9A-Za-z+/=`. Used by LDAP and some Java password formats.
- **crypt(3) base64:** a peculiar alphabet `./0-9A-Za-z` (note the `.` and `/` at the start, no `=` for padding). Used by bcrypt and the old Unix crypt formats.
# Salts in Cryptographic Hashing 

A Salt is a unique, randomly generated string of characters combined with a user's password before running it through a cryptographic hash function

## The problem it solves
If two users happen to choose the exact same password, and the system uses a plain hash function 

$$\text{MD5}("hunter2") = \text{f52fbd32b2b3b86ff88ef61f3d728045}$$
Both users will have the exact same hash string stored in the database. This exposes the application to two major vulnerabilities: 
- Pattern recognition: An attacker with access to the database can instantly identify users sharing the same password
- Rainbow tables: Attackers leverage precomputed lookups tables containing billions of plaintexts alongside their corresponding hashes. Cracking a stolen hash becomes as fast as performing a simple database query
## How salting works

When a user creates or updates their password, the application executes the following workflow:
1. Generation: Create a unique, pseudo-random string for that user
2. Concatenation: Combines the raw password with the salt
3. Hashing: Pass the combined string through the hashing algorithm
4. Storage: Save both the salt and the resulting hash in the database
$$\text{Final Digest} = \text{Hash}(\text{Password} + \text{Salt})$$
# Why identification has to become first

Offensive security tools like Hashcat or John the Ripper do not guess generically. They require a specific mode parameter (e.g., Hashcat -m 0 for MD5, -m 1000 for NTLM). The tool must construct the exact mathematical transformation in GPU memory before running candidate guesses. Without identifying the algorithm first, you cannot set the execution mode.
